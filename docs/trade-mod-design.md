## 0. ローダー選定：Fabric を推奨

| 観点 | Fabric | NeoForge |
|---|---|---|
| 最新版への追従 | 速い（スナップショットから追従） | やや遅れることがある |
| 本Modに必要な機能（アイテム/ブロック/画面/通信/SavedData/データパック/コマンド） | すべて Fabric API で可 | すべて可 |
| 設定ファイル | 標準機能なし（自作 or ライブラリ） | `ModConfigSpec` が標準 |
| 学習資料 | 公式Docsが整理されている、軽量で全体像を掴みやすい | Docs充実、ただし仕組み（イベントバス/Capability等）が多い |
| ビルドの軽さ | 軽い | やや重い |

**結論：Fabric のままでよい。** 本Modはバニラのクラスに深く手を入れず（Mixin は必要な所だけに使う：財布の自動収納（E-6）、村のテンプレートプールへの建物の追加（段階9）、村人交易のコイン化（H章）など）、独自ブロック・独自画面・独自データで完結する設計にするため、NeoForge の強み（Capability、標準Config、大型Mod連携）がほとんど効きません。唯一の不足は Config ですが、JSON + Codec で自作します（G章）。
NeoForge を選ぶべきなのは「Create 等の NeoForge 専用大型Modと同じModパックに入れたい」場合のみです（Q4）。

## 2. 推奨仕様

### A. 交易の窓口

#### A-1. 方式比較

| 方式 | 内容 | 長所 | 短所 | 難易度 |
|---|---|---|---|---|
| ① バニラ村人交易を置き換え | 村人の `MerchantOffers` を動的価格に差し替え | 既存の村をそのまま使える | バニラの交易UIは「1オファー=固定の入力→出力」「使用回数」前提で、数量指定・売り/買い両方向・相場表示に向かない。Mixin多用、村人の職業/レベル/値引き（評判）と衝突 | 高 |
| ② 村人交易を拡張 | 村人に右クリック→独自UIを追加 | 村と紐づく | 村人のAI・職業ブロック・ゾンビ化など挙動の整合が大変。他Mod・バニラ更新に弱い | 中〜高 |
| ③ 新規 交易ブロック（屋台） | ブロックを右クリックで独自UI | 実装が最も単純。位置が固定なので「市場」の位置が明確。Mixin不要 | 「人と取引している感」は弱い | **低** |
| ④ 新規 商人NPC | 独自エンティティ（村人風） | 雰囲気が良い。村に住まわせられる | エンティティ登録・モデル・AI・スポーン・保護が必要 | 中〜高 |

#### A-2. 推奨
**③交易ブロックを先に作り、④商人NPCを後から追加。両者は同じ「市場（Market）」バックエンドを使う。**

- フェーズ1（5章の段階0〜8）：`交易所ブロック（Market Stall）`。右クリックで交易画面。ブロック位置から所属市場を決定。
- フェーズ2（段階9〜10）：村への自然生成と`商人NPC（Trader）`。商人NPCは交易所を開いた時に交易所の前に1体出るほか、スポーンエッグとコマンドでも出せる。右クリックで同じ画面（A-5）。村の生成時に出す処理も段階10で作る（段階9は v0.14 で実装済み、5-1）。
- フェーズ3（段階11以降）：仕上げ・オプション機能（村人交易の無効化など）。
- バニラ村人の交易は残す。設定 `vanilla.disableVillagerTrades` で無効化に切り替えられる（フェーズ3、Q5）。
- 【v0.12】村人から買う時の代金はコインにする（H章、Q36）。Q5 の「触らない」方針はここで変更した。

#### A-3. 交易所ブロック仕様

| 項目 | 内容 |
|---|---|
| ID | `trade_expansion:market_stall` |
| 形状 | 屋台風（向きあり、`HORIZONTAL_FACING`） |
| 入手 | 村に自然生成（屋台入りの建物ピースを村のテンプレートプールに追加、段階9）＋クラフト（仮レシピ：1段目 カーペット×3／2段目 木材・エメラルド・木材／3段目 木材・樽・木材。`#minecraft:wool_carpets`, `#minecraft:planks`） |
| 採掘 | 斧（`#minecraft:mineable/axe`）。ドロップは自身 |
| 形状（現状） | 屋台風のモデル（カウンター・柱・縞模様の日よけ・商品。v0.14、段階11）。当たり判定もモデルの形（北向きの形を向きに合わせて回転）。光を通す（`noOcclusion`） |
| ブロックエンティティ | 持つ（`market_id` を long で保存。未割当は `-1`）。**プレイヤーが設置した時**はその場で市場を割当（生成元 `crafted`）。**プレイヤー以外の方法で置かれたもの**（自然生成・`/setblock` 等）は、最初に右クリックされた時に割当（生成元 `natural`）。ワールド生成は別スレッドで動くため、生成中に SavedData を触らない。【v0.4.1】生成元 `origin`（`natural`/`crafted`）も一緒に保存する（段階8で実装済み） |
| 割り当て直し（v0.4.1） | 所属市場が `/tradeex market delete`（4-2）で削除されていた場合、次の右クリックで割り当て直す。判定には**保存した生成元**を使う（クラフト品は C-1 の最小距離制限がそのままかかり、自然生成品はかからない）。クラフト品が制限に引っかかった時は、画面を開かずに理由をチャットに表示し、**ブロックは壊さない**（設置時と違い、他人の屋台を右クリックしただけで壊れるのを防ぐ。プレイヤーは壊して置き直す）。`origin` が保存されていない古い屋台は、`market_id = -1` なら `natural`、それ以外なら `crafted` とみなす（制限がかかる安全側） |
| 設置の拒否（C-1） | 実装上は「いったん設置 → 割当に失敗したら即座に破壊」。サバイバルではアイテムが戻り、クリエイティブでは戻らない。理由（最寄り市場までの距離、統合半径、最小距離）をチャットに表示 |

### B. 価格モデル

#### B-1. 用語と状態変数

全ての金額は **銅貨単位（c）の整数 `long`** で扱う。

| 記号 | 名前 | 種類 | 説明 |
|---|---|---|---|
| `B` | 基準価格 | 計算値 | その市場でのこの商品の標準価格（c）。商品定義・プロファイル・ばらつき・不足品の倍率から D-1 の式で計算する |
| `X` | 需給圧（pressure） | 状態（double） | 売られると＋、買われると−。0が平常 |
| `τ` | 弾力性（elasticity） | 定義値 | `X` がいくつで価値が 1/e（約37%）になるか。大きいほど値崩れしにくい |
| `V` | 価値倍率 | 計算値 | `V = clamp(exp(−X/τ), Vmin, Vmax)` |
| `s` | 売買スプレッド | 定義値 | 買値と売値の差の割合 |
| `S` | 在庫 | 状態（double） | 購入で −1、売却で +1 |
| `T` | 目標在庫 | 定義値 | 平常時に戻る在庫量 |
| `Scap` | 在庫上限 | 定義値 | これ以上は買い取らない。商品定義の `max_stock`、無ければ `T × price.defaultMaxStockMultiplier`（既定2.0） |
| `H` | 回復半減期 | 設定値 | `X` が半分に戻るまでの時間（ゲーム内日）。商品定義の `half_life_days`、無ければ設定値（消耗品は別の設定値、B-3） |
| `r` | 補充速度 | 定義値 | 在庫が `T` より少ない時に `T` に向かって増える速さ（個/日） |
| `c` | 消費量 | 定義値 | 在庫が `T` より多い時に減る速さ（個/日）。商品定義の `consume_per_day`、無ければ `r/2`（消耗品は `T × recovery.consumableMultiplier`、B-3。v0.14.1） |

#### B-2. 価格の数式

```
V        = clamp( exp(−X / τ), Vmin, Vmax )
買値 Pbuy  = max(1, ceil ( B × V × (1 + s/2) ))   … プレイヤーが買う値段（切り上げ）
売値 Psell = max(1, floor( B × V × (1 − s/2) ))   … プレイヤーが売る値段（切り捨て、最低1c）
```

- 「売りすぎると価値が下がる」＝売るたびに `X += 1`、`V` が指数的に下がる（同じ次元の他の市場には C-2 の重み `w(d)` を掛けて波及）。
- 「買いすぎると高くなる＆売り切れ」＝買うたびに `X −= 1`、`S −= 1`（波及は売りと同じ）。`S < 1` で購入不可。
- 丸めを「買値は切り上げ・売値は切り捨て」にすることで、安い商品でも常に 買値 ≥ 売値 となる（四捨五入だと数cの商品で両者が一致し得る）。
- 指数関数にする理由：何個目でも「1個あたり一定割合」で下がるので直感的、かつ0以下にならない。
- 変化量の上下限：`V` を `[Vmin, Vmax]` にクランプ（既定 0.25〜3.0）。さらに `X` 自体も `[−τ·ln(Vmax), τ·ln(1/Vmin)]` にクランプし、上限を超えて溜まらないようにする（回復が不自然に遅れるのを防ぐ）。

#### B-3. 時間による回復（遅延評価）

毎tick全市場を更新するのは重いので、**市場にアクセスした時に経過時間から一括計算**する（lazy update）。

```
Δt = (現在の gameTime − lastUpdateGameTime) / 24000      … ゲーム内日数
X ← X × 2^(−Δt / H)                                      … 半減期で 0 へ戻る
S ← S < T ? min(T, S + r·Δt)  :  max(T, S − c·Δt)         … 在庫は T へ戻る（過剰在庫は消費量 c で減る）
lastUpdateGameTime ← 現在
```

- 時刻は `level.getGameTime()`（ワールドの累計tick）を使う。`/time set` や寝ることで巻き戻らない／飛ばない。
  - 寝てスキップした分も回復させたい場合は設定 `recovery.clock = DAY_TIME` に切替（既定 `GAME_TIME`）。
  - `DAY_TIME` では `/time set` で時刻が戻ることがあるため、`Δt < 0` の場合は `Δt = 0` として扱い、`lastUpdateGameTime` を現在値に更新する。
  - クライアントのプレビューも同じ時計で計算する必要があるため、スナップショットには選んだ時計の時刻を入れ、`recovery.clock` をクライアントに同期する（F-2、G章）。
- サーバー停止中は時間が進まないので回復もしない（自然）。
- r と c には全体倍率 `recovery.restockMultiplier` を掛ける。
- 【v0.14.1】**消耗品**：食料・松明・燃料・原木・木材など、市場で使われてなくなる品は、在庫も買取数も早く回復させる。
  - 対象はアイテムタグ `#trade_expansion:consumables`（同梱：作物・野菜・果物・生肉・魚・料理・卵・牛乳・砂糖・コーラスフルーツ・松明・魂の松明・石炭・木炭・`#minecraft:logs`・`#minecraft:planks`・棒・丸石・砂・ガラス）。腐った肉・金のリンゴ・金のニンジンは入れない（消費される品ではない、または高級品のため）。
  - 【v0.14.2】**後から追加・削除できる**：①データパックでタグを上書き、②設定 `consumables.add`（タグに無くても消耗品にするアイテムID）・`consumables.remove`（タグにあっても消耗品にしないアイテムID）、③管理コマンド `/tradeex consumable add|remove|reset <アイテム>`（②の一覧を書き換えて設定ファイルを読み直す。`reset` は②から消してタグの指定に戻す）、`/tradeex consumable list`（今の消耗品の商品と②の内容）。判定は「`remove` にある → 消耗品でない、`add` にあるかタグにある → 消耗品」。設定画面では「回復」タブの一覧で編集できる。
  - 消耗品かどうかは価格の計算のたびに判定するので、変更はすぐに全市場へ反映する（過去の在庫・相場はそのまま、以降の回復の速さが変わる）。開いている交易画面は次のスナップショットから新しい値で計算する。
  - 消費量 c：商品定義の `consume_per_day` → 無ければ、消耗品は `T × recovery.consumableMultiplier`（既定 1.0。上限まで売られても1日で T に戻る）、それ以外は `r / 2`（v0.14 までと同じ）。
  - 半減期 H：商品定義の `half_life_days` → 無ければ、消耗品は `recovery.consumableHalfLifeDays`（既定 1.0）、それ以外は `recovery.halfLifeDays`。
  - 例：ニンジン（T＝64、上限128、r＝32）は、上限まで売っても翌日（現実の20分後）には64個まで消費され、また64個売れる。相場のずれも1日で半分に戻る。
  - 解決した c と H は市場ごとのパラメーターに入れてスナップショットで送るので、クライアントのプレビューも同じ値で計算する（F-2）。

#### B-4. 売り切れと復活

| 状態 | 条件 | 挙動 |
|---|---|---|
| 通常 | `1 ≤ S` | 購入可 |
| 売り切れ | `S < 1` | 購入不可。UIに「次の入荷まで」= `(1 − S)/r` 日を表示 |
| 復活 | 回復計算で `S ≥ 1` | 自動で購入可に戻る（イベント不要） |
| 買取停止 | `S ≥ Scap` | その商品は売却不可（市場が抱えきれない） |
| 非取扱 | 定義で `buy:false` / `sell:false` | その方向の取引なし（例：買取専門の商品） |

- プレイヤーが売った品は在庫に入り、他プレイヤーが買える（市場が流通を仲介する）。

#### B-5. まとめ売買の価格（逐次計算）

n個まとめて売買する時の合計は「1個ずつ取引した場合の合計」と一致させる（分割取引で得をしない）。

```
売却合計 = Σ_{k=0}^{n−1} Psell( X + k )      … 1個売るごとに X が +1
購入合計 = Σ_{k=0}^{n−1} Pbuy ( X − k )      … 1個買うごとに X が −1
```
n は最大でもインベントリ分（2,304個）なのでループで十分。

**取引単位（v0.6）**：商品定義の `unit`（既定1）が2以上の商品は、`unit` 個を1単位として扱う。価格（B・Pbuy・Psell）・在庫（S・T・Scap）・需給圧 X の変化・上の n はすべて**単位の数**で数え、アイテムの移動だけ `n × unit` 個になる。所持数などの判定は `floor(所持数 ÷ unit)` 単位で行う。

**足りない場合の扱い（部分約定しない）**：

- プレビュー時に「可能な最大数量」を計算して表示する。購入なら `min(floor(S), 所持金で買える数, インベントリの空き)`、売却なら `min(所持数, floor(Scap − S))`。
- 確定時に指定数量を全部取引できなければ**取引全体を中止**する。期待額チェック（A-4）と同じく「見た額と違う取引は成立しない」で統一する。
- 中止時、サーバーは結果コードと**市場の最新スナップショット**を送り直す。最大数量はサーバーから返さず、クライアントがスナップショットと自分のインベントリから再計算する（v0.4 で変更）。

##### 結果コード（`TradeResult`）

| コード | 意味 |
|---|---|
| `SUCCESS` | 成立 |
| `INVALID_REQUEST` | 市場が存在しない／開いている画面の市場IDと不一致／数量が 0 以下または `trade.maxPerTransaction` 超（Shift で全数の時は 2,304 超） |
| `TOO_FAR` | 屋台（商人NPCから開いた時は商人）が無くなった、または `trade.maxDistance` より離れている |
| `CREATIVE_NOT_ALLOWED` | クリエイティブモードで `trade.allowCreative=false` |
| `NOT_AVAILABLE` | その市場に無い商品、定義が消えた商品、`buy`/`sell` が false の方向 |
| `INSUFFICIENT_STOCK` | 購入数 > floor(S) |
| `INSUFFICIENT_FUNDS` | 所持金不足 |
| `INSUFFICIENT_ITEMS` | 売却数 > 所持数（インベントリと売却スロットの品を数える。`components` 指定の無い商品は付加情報なしの通常品だけ、指定のある商品はその付加情報と一致する品だけ。減額買取が有効な商品は耐久減少品も数える、A-4・D-2） |
| `INVENTORY_FULL` | 購入品がインベントリに入らない |
| `STOCK_FULL` | 売却数 > floor(Scap − S) |
| `PRICE_CHANGED` | サーバーの合計額がプレビュー額から許容範囲を超えてずれた |
| `CARD_INVALID` | カード払いを選んだが、有効なカード（自分のもので最新の番号）を持っていない（v0.11、E-8） |

検証の順序：`INVALID_REQUEST` → `TOO_FAR` → `CREATIVE_NOT_ALLOWED` → `CARD_INVALID` → `NOT_AVAILABLE` →（遅延回復）→ 在庫系（`INSUFFICIENT_STOCK` / `STOCK_FULL`）→ `PRICE_CHANGED` → 所持系（`INSUFFICIENT_FUNDS` / `INVENTORY_FULL` / `INSUFFICIENT_ITEMS`）。

#### B-6. 搾取防止の条件

同一市場で「売る→すぐ買い戻す」で利益が出ない条件：
`(1 + s/2)/(1 − s/2) > exp(1/τ)`。既定 `s = 0.4` なら左辺 1.5 → **τ > 2.47** なら安全。スプレッドを小さくすると必要な τ は大きくなる（例：`s=0.05` なら τ > 20）ため、設定範囲だけでは保証できない。ロード時に商品ごとに検証し、違反する定義は警告＋`τ` をこの条件を満たす値に補正する（補正後の値 = `1 / ln((1+s/2)/(1−s/2)) × 1.01`、つまり安全な最小値に1%の余裕を足す。実装：`PriceModel.ensureExploitSafe`。警告ログは段階7のデータパック読込で出す）。
（クラフト経由の裏技：安い素材を買って高い完成品を売る、は管理コマンド `/tradeex audit`（4-2、段階11）で検出する）

#### B-7. 既定値

| パラメータ | 既定値 | 備考 |
|---|---|---|
| `s`（スプレッド） | 0.4 | 買値 = 基準×1.2、売値 = 基準×0.8 |
| `τ`（弾力性） | 商品ごと。既定 32、高額品 16、大量流通品（小麦等）128 | |
| `Vmin` / `Vmax` | 0.25 / 3.0 | |
| `H`（半減期） | 2.0日（消耗品は 1.0日） | Q11（v0.5 で 1.0 → 2.0）。消耗品は v0.14.1 |
| `T` / `r` | 商品ごと。既定 `T=16`, `r=T/2`（2日で満タン） | |
| `c` | 商品ごと。既定 `r/2`、消耗品は `T`（1日で目標在庫まで戻る） | v0.14.1、B-3 |
| `Scap` | `max_stock`、無ければ `2T` | |

### C. 距離による影響

#### C-1. 「市場」の単位：**市場ノード（交易所ごと）＋近接統合**

| 案 | 長所 | 短所 |
|---|---|---|
| 村単位 | 直感的 | 村の判定が曖昧（バニラに「村」オブジェクトは無い。POIの集まりでしかない）、クラフト設置に対応しにくい |
| チャンク/グリッド単位 | 計算が単純 | グリッドの境目で隣の家同士が別市場になる不自然さ |
| **ノード＋統合（推奨）** | 交易所の位置が市場。近くの交易所は同じ市場に統合 | 統合ロジックが必要（簡単） |

- **市場ノード**：交易所ブロックの市場割当時（A-3）、同じ次元で半径 `mergeRadius`（既定 **64ブロック**、水平距離）以内に既存市場があればそこに所属、なければ新しい市場を作る。中心座標は最初の交易所の位置。
  - 同じ村の複数の屋台は1つの市場＝**在庫も相場も完全に共通**。
  - `mergeRadius` 内に市場が複数ある場合は、**中心が最も近い市場**に所属する（等距離なら ID の小さい方）。
  - クラフトした屋台も同じルールで、近くに市場があればそこに所属する（Q12）。
  - 【v0.13】商人NPC（A-5）は既存の市場に所属するだけで、新しい市場は作らない。
- **新規市場の制限**：クラフトした屋台で新しい市場を作れるのは、同じ次元の既存市場の中心から `distance.minNewMarketDistance`（既定 **256ブロック**）以上離れた場所だけ。条件を満たさない場合は設置を拒否し、理由をメッセージ表示する（屋台を置き直して相場をリセットする抜け道を防ぐ。拒否の実装方法は A-3）。自然生成の屋台にはこの制限をかけない。
  - 判定のまとめ：最寄り市場までの距離 d について、`d ≤ mergeRadius` → その市場に所属／`mergeRadius < d < minNewMarketDistance` → クラフト品は拒否・自然生成品は新規市場／`d ≥ minNewMarketDistance` → 新規市場。
- **新規市場の品揃え**：プロファイルと市場レベルによる 10〜20 商品の抽選（D-1・D-4、段階7で実装）。`priceFactor` などの乱数シードは `ワールドシード ^ (中心座標.asLong() × 0x9E3779B97F4A7C15)`。
- **新規市場の初期相場**：新しい市場の各商品の `X` は 0 ではなく、周辺市場の相場の距離重み付き平均から始める。
  ```
  Rnear 以内に同じ商品を扱う市場がある → X_new = それらの X の平均（近場は同じ相場）
  無ければ                             → X_new = Σ_j ( w(d_j) × X_j ) / Σ_j w(d_j)   … j は Rfar 以内の市場
  周辺に該当市場が無い（Σw = 0）       → X_new = 0
  （各市場の X は refresh 後の値を使う）
  ```
  在庫 `S` は `T` から始める。これにより「近場（Rnear以内）は同じ相場」が後から作った市場でも保たれる。
- 市場が保持する交易所が0になっても市場データは残す（再設置で復活）。
- 【v0.4.1】管理者が市場の相場を戻したい時は、市場を削除せず `/tradeex market reset` で状態だけ初期化する（市場IDが残るので屋台の割り当て直しは起きない）。市場そのものを消す `/tradeex market delete` を使った場合、所属していた屋台は次の右クリックで割り当て直され、クラフト屋台には上の新規市場の制限がかかる（A-3）。

#### C-2. 距離減衰（相場の波及）

ある市場Aで取引して `ΔX` が発生したら、同じ次元の他の市場Bにも波及させる：

```
d = 市場A中心と市場B中心の水平距離（ブロック）
w(d) = 1                                  (d ≤ Rnear)
     = ((Rfar − d) / (Rfar − Rnear))^p     (Rnear < d < Rfar)
     = 0                                  (d ≥ Rfar)
ΔX_B = ΔX_A × w(d) × 商品の連動係数 link（既定1.0）
```

| パラメータ | 既定 | 意味 |
|---|---|---|
| `mergeRadius` | 64 | この範囲は同じ市場（在庫も共通） |
| `Rnear` | 128 | ここまでは **相場（X）が100%共通**＝「近場は同じ」 |
| `Rfar` | 1536 | ここから先は影響0 |
| `p` | 2.0 | 減衰カーブ。1＝直線、2＝Rnearを出た直後に大きく下がり、遠方ではなだらかに0へ |

- 波及するのは **相場（X）だけ**。在庫（S）は波及しない（遠くの店の棚が空になるのは不自然）。
- 波及先がその商品を扱っていない場合は無視。扱いがあるが `B` が違っても `X` で波及するので「割合」で連動する。
- 計算量：市場は多くて数百。空間インデックス（512ブロックのセルでハッシュ）で `Rfar` 内だけ走査する予定（`MarketIndex`）。v0.15 時点は全件走査で代用している（市場が数百でも問題ない量）。

#### C-3. ネザー・エンド

| 次元 | 既定の扱い |
|---|---|
| オーバーワールド | 通常 |
| ネザー | 扱う商品はネザー用のプロファイルで決まる（D-2、Q10）。独立した市場群（オーバーワールドへ波及しない）。設定 `distance.linkNetherToOverworld=true` で、ネザー座標×8 をオーバーワールド座標とみなして相互波及 |
| エンド | 扱う商品はエンド用のプロファイルで決まる。独立。距離計算は通常通り（外縁の島同士でも波及） |
| 他Modの次元 | 独立（`trade_expansion:default` プロファイル） |

- 次元ごとに扱う商品が異なる（Q10）ため、`distance.linkNetherToOverworld=true` でも波及するのは**両方の次元の市場が扱っている商品だけ**（C-2 の「波及先が扱っていない商品は無視」による）。
- `distance.linkNetherToOverworld` は v0.15 時点で未実装（設定値だけある）。

#### C-4. 市場名【v0.15 追加】

市場に名前を付けられる。名前が無い市場は自動の名前で表示する。

| 項目 | 内容 |
|---|---|
| 名札で名付け | 金床で名前を付けた名札を持って交易所を右クリックすると、その交易所の市場の名前になる。サバイバルでは名札を1枚使う（クリエイティブでは減らない）。名前の無い名札で右クリックした時は普通に交易画面を開く |
| 名前付きの交易所 | 金床で名前を付けた交易所を置いて**新しい市場を作った時**だけ、その名前を市場名にする。既存の市場に加わる時は名前を使わない |
| 管理コマンド | `/tradeex market name <ID> <名前>`（名前は空白を含んでもよい）、`/tradeex market name <ID> reset`（名前を消して自動の名前に戻す）。権限は他の管理コマンドと同じ（`command.permissionLevel`） |
| 自動の名前 | 名前が無い時は「プロファイルの表示名 #ID」（例：平原の村 #12）。プロファイルに表示名が無ければ「市場 #12」 |
| 表示 | 交易画面のタイトル・掲示板の市場一覧（I章）は「名前（レベル名）」。交易所を置いた時のメッセージ、`/tradeex market info` にも出す |
| 名前の扱い | 書式コード（色など）を外し、前後の空白を除き、最大32文字に切る。空になる名前は使わない |
| 変えられる人 | 設定 `market.renamePermission`：`NAMER_OR_OP`（既定）＝ OP と「名付け親」、名付け親がまだいない市場は誰でも／`ANYONE`＝誰でも／`OP_ONLY`＝OP だけ。名付け親は、プレイヤーが作った市場では最初の交易所を置いた人、それ以外では最初に名前を付けた人。シングルプレイの持ち主はいつでも変えられる。管理コマンドはこの制限を受けない |
| 保存 | 市場の保存データに名前と名付け親の UUID を持つ（F-1）。市場を削除すれば消える |

- 変えられない時は理由をアクションバーに出し、名札は減らさない。
- 開いている交易画面のタイトルは開き直すまで変わらない。

### D. 地域ごとの品揃え

#### D-1. 決定ロジック

市場が**作られた時に**決定し、保存する。その後は**市場のレベルが上がった時だけ商品を追加**する（D-4）。後でデータパックを変えたら `/tradeex market reroll` で再抽選。

1. 市場位置の情報を集める：次元、バイオーム（タグ）、含まれる構造物（村・前哨基地など）、村タイプ（バイオームから `VillagerType` 相当を導出：plains/desert/savanna/snow/taiga/jungle/swamp）、生成元（自然生成 or クラフト設置）、**市場レベル**（D-4）。
2. 全 `market_profile` の `conditions` を評価し、合致したものから `priority` が最も高いものを採用（同点は `weight` で抽選）。プロファイルは一度決めたら保存し、レベルが上がっても変えない。
3. 商品を選ぶ。目標の商品数 `N` は市場レベルから決まる（D-4。`market.minGoods`〜`market.maxGoods`、既定 10〜20）。
   0. 商品定義に `auto_add` 条件がある商品（例：エメラルド貨）は、プロファイルに関係なく、条件に合う市場に入れる。これは `N` に数えない別枠。
   1. `always` の商品を入れる。
   2. 各 `pools` から `rolls` 回抽選する。候補は `min_level` ≤ 市場レベル の項目だけで、選ばれた商品は候補から外す（重複なし）。
   3. 数を `N` に合わせる：足りなければ、全プールの候補から重みに従って重複なしで追加抽選する。多ければ、`always` 以外からランダムに外す。候補が尽きて `N` に届かない場合は、ある分だけで作り、警告ログを出す。
   - 乱数のシードは `ワールドシード ^ 市場中心座標のハッシュ` → **同じ場所なら同じ品揃え**（再現性あり）。レベルが上がって商品を追加する時（D-4）は、シードに新しいレベルを混ぜる（`… ^ レベル`）。
4. 各商品について、ばらつき係数 `priceFactor = 1 + 乱数(−price.jitter 〜 +price.jitter)`（既定 ±15%）を抽選して**保存する**。
5. 基準価格は保存せず、使うたびに次の式で計算する：
   ```
   B = goods定義の base_price × プロファイルの倍率（base_price_multiplier × price_modifiers） × priceFactor × price.globalMultiplier
       × 不足品の倍率（K章。不足品でなければ 1）
   ```
   こうすることで、データパックで `base_price` を変えて `/reload` すると、既存市場にも反映される。

#### D-2. データパック形式

配置：`data/<namespace>/trade_expansion/market_profile/<name>.json` と `data/<namespace>/trade_expansion/goods/<name>.json`

**商品定義（goods）**：商品のデフォルト値

```json
// data/trade_expansion/trade_expansion/goods/diamond_sword.json
{
  "item": "minecraft:diamond_sword",
  "base_price": 900,
  "elasticity": 16,
  "target_stock": 8,
  "max_stock": 24,
  "restock_per_day": 4,
  "spread": 0.4,
  "buy": true,
  "sell": true,
  "accept_damaged": false
}
```

- `buy` / `sell` は**プレイヤー視点**（`buy`=プレイヤーが買える、`sell`=プレイヤーが売れる）。
- 【v0.6】任意項目 `unit`（取引単位、既定1）：この数をまとめて1単位として売買する（B-5）。1個あたりの価値を 1c 未満にしたい商品に使う。
- 【v0.14.1】任意項目 `consume_per_day`（在庫が目標より多い時に1日に減る数）と `half_life_days`（相場のずれの半減期）：省略時は B-3 の消耗品の扱いに従う。
- 【v0.6】任意項目 `auto_add`（条件のリスト。書式は market_profile の `conditions` と同じ）：書いてあれば、プロファイルに関係なく条件に合う市場がこの商品を扱う（D-1 手順0。商品数 `N` とは別枠）。空のリスト `[]` なら全市場。省略時は自動追加しない。条件は市場を作った時と `market reroll` の時に評価する。
- 省略可能な項目（`elasticity`, `max_stock`, `spread`, `accept_damaged` など）は省略すると全体設定（G章）の既定値を使う。**商品定義に書いてあればそちらが優先**。
- 付加情報（データコンポーネント）で区別が必要な商品は、任意項目 `components` で絞り込む。指定した付加情報が一致するアイテムだけを同じ商品として扱い、購入時はその付加情報を付けたアイテムを渡す。

```json
// data/trade_expansion/trade_expansion/goods/potion_healing.json
{
  "item": "minecraft:potion",
  "components": { "minecraft:potion_contents": { "potion": "minecraft:healing" } },
  "base_price": 120
}
```
※付加情報の書式は 26.3 のアイテムコンポーネントの JSON 形式（`/give` のコンポーネントと同じ、バニラのコーデックで読む）。同梱データには `components` 付きの商品はまだ無く、実際の読み込みはゲーム内で未確認。`components` 未指定の商品は「付加情報なし（通常品）」のみ一致する（名前付き・エンチャント付きは別物として扱い、買い取らない。耐久減少品だけは減額買取が有効な時に例外として一致する、A-4）。

- 【v0.14】`components`・減額買取（`accept_damaged`）の取引処理と、C-2 の連動係数 `link`（任意項目、既定 1.0、0〜10）を段階11で実装した。`components` はサーバーの登録情報で解決してキャッシュし（`/reload` で作り直す）、購入時はその付加情報を付けて渡す。減額買取は耐久だけが減った品を残り耐久の割合で買い取る（売却額 = floor(通常の売値 × 残り耐久の割合)、最低1c。まず無傷の品から使う）。

|---|---|---|
| `trade_expansion:dimension` | `dimension` | 次元一致 |
| `trade_expansion:biome` | `biome`（ID or `#タグ`） | 中心座標のバイオーム |
| `trade_expansion:structure` | `structure`（ID or `#タグ`） | 中心がその構造物内 |
| `trade_expansion:villager_type` | `villager_type`（例：`minecraft:plains`） | 村タイプ（v0.7：引数名を `type` から変更。条件の種類を表す `type` と重なるため） |

| `trade_expansion:distance_from_spawn` | `min`/`max` | スポーンからの距離（遠いほど高級品、等） |

- **ディメンションごとに扱う商品を変える**（Q10）：プロファイルは原則 `trade_expansion:dimension` 条件で対象の次元を指定する。何も合致しない場合は、次元ごとの既定プロファイル `trade_expansion:default_overworld` / `default_the_nether` / `default_the_end` を使う（他Modの次元は `trade_expansion:default`）。いずれも `priority: 0`、条件なし。
- データパックは `/reload` で再読込。既存市場の**商品構成は変えない**が、`base_price`・`τ` 等の定義値は再読込値を使う（保存している状態 `X`, `S`, `priceFactor` は保持。`B` は D-1 の式で再計算）。

#### D-3. 同梱する初期データ（目安）

> 具体的な商品一覧（60種の価格・弾力性・在庫）と各プロファイルの候補・重み・`min_level` は別紙 [goods-design.md](goods-design.md)（商品・品揃え設計書）にまとめる。別紙は v0.7 で採用し、その検討事項 G1〜G3 を本書に反映済み。

既定プロファイル：

- オーバーワールド：平原の村・砂漠の村・サバンナの村・雪原の村・タイガの村（`plains_village` 等）、ジャングル・沼地（`jungle`・`swamp`）、クラフト屋台（`crafted_stall`）、`default_overworld`
  - バニラの村は平原・砂漠・サバンナ・雪原・タイガの5種類だけで、**ジャングルと沼地には村が生成されない**。そのため `jungle`・`swamp` は村の条件を付けず、そのバイオームにプレイヤーが作った市場向けのプロファイルにする（v0.7 で修正）。
- ネザー：ピグリン風（金・ネザー素材）＝`default_the_nether`
- エンド：エンダーパール・シュルカー殻など＝`default_the_end`
- 他Modの次元：`default`

商品数：初期 60種（ネザー8種・エンド4種を含む。別紙 2章）。ほかに村の市場共通のエメラルド貨（E-5）。エメラルドそのもの（`minecraft:emerald`）は商品にしない（Q24）。1市場が扱うのはそのうち 10〜20種（D-4）なので、各プロファイルの候補は最大レベルの商品数（20）以上を用意する。

#### D-4. 市場の規模（レベル）【v0.5 追加】

村・町の規模に応じて市場のレベルが決まり、**レベルが高いほど扱う商品が多く、高級品も並ぶ**。

**規模の測り方**：次元によって測るものが違う。

- **オーバーワールド・他Modの次元**：市場の中心から水平半径 `market.levelRadius`（既定 64）以内にある**ベッドの数**（村人やプレイヤーの家を表す `minecraft:home` POI。`PoiManager` で水平距離を見て数える。高さは問わない）。村は家が多いほどベッドが多く、プレイヤーが作った町も家を建てるほど育つ。
- **ネザー・エンド**（v0.7、Q27）：ベッドが使えない（爆発する）ため、同じ水平半径・上下 ±32 ブロック以内にいる**村人（`minecraft:villager`）の人数**。行商人・ゾンビ村人は数えない。村人はネザー・エンドでは増やせないので、プレイヤーがポータルで連れて来た人数が市場の規模になる。村人はエンティティなので、周りのチャンクが読み込まれている必要があるが、測るのは誰かが画面を開いた時なので通常は問題にならない。

| レベル | 名前 | ベッド数（既定） | 村人の人数（ネザー・エンド、既定） | 商品数 N（既定 10〜20 の場合） |
|---|---|---|---|---|
| 1 | 集落 | 0〜4 | 0〜2 | 10 |
| 2 | 村 | 5〜9 | 3〜5 | 13 |
| 3 | 大きな村 | 10〜19 | 6〜11 | 15 |
| 4 | 町 | 20〜39 | 12〜23 | 18 |
| 5 | 都市 | 40〜 | 24〜 | 20 |

- 境目は設定 `market.levelThresholds = [5, 10, 20, 40]`（ベッド数）と `market.villagerThresholds = [3, 6, 12, 24]`（村人の人数。連れて来るのはベッドを置くより大変なので低めにする）。
- 商品数 `N = round(minGoods + (maxGoods − minGoods) × (レベル − 1) / 4)`。
- **測るタイミング**：市場を作った時と、誰かが画面を開いた時（ただし前回からゲーム内 `market.levelCheckIntervalDays`＝既定1日以上たっている場合だけ。POI の検索は重いため）。
- **レベルが上がった時**：新しい `N` になるまで、D-1 手順3と同じ方法（新しいレベルで候補になった `min_level` の商品を含む）で商品を追加する。追加した商品の `X` は C-1 の新規市場の初期相場と同じ計算、在庫 `S` は `T` から始める。画面を開いたプレイヤーに「市場が『町』に成長しました」のように知らせる。
- **レベルが下がった時**（ベッドが壊された、村人が死んだ等）：レベルは最高到達値を保持し、商品は減らさない（Q21）。
- 画面のタイトルにレベル名を出す（例：「平原の村 #12（町）」。市場名は C-4）。`/tradeex market info` でもレベルとベッド数（ネザー・エンドは村人の人数）を表示する。
- `/tradeex market reset` はレベルと商品構成を保持し、`market reroll` は現在のレベルで商品を選び直す。
- 割り切り：ベッドを大量に置けばレベルを上げられる。ネザー・エンドでも村人を一時的に連れて来ればレベルが上がり、その後いなくなっても下がらない。どちらも手間に見合う程度の効果なので許容する。
- 【v0.12】レベルに「村人と紐付いたベッド（ネザー・エンドは職業ブロック）が1つ以上」という条件を付けるかを検討中（L-1、Q38 保留）。

### E. 通貨

#### E-1. コイン5種

所持金として数え、支払いに使えるのは次の5種類。補助コインのエメラルド貨は所持金に数えない（E-5）。

比率 `R`（既定 10）。内部価値は銅貨単位。

| コイン | ID | 価値（c）既定比率の場合 | 一般式（全段が同じ比率 R の場合） | スタック |
|---|---|---|---|---|
| 銅貨 | `trade_expansion:copper_coin` | 1 | 1 | 64 |
| 鉄貨 | `trade_expansion:iron_coin` | 10 | R | 64 |
| 金貨 | `trade_expansion:gold_coin` | 100 | R² | 64 |
| ダイヤ貨 | `trade_expansion:diamond_coin` | 1,000 | R³ | 64 |
| ネザライト貨 | `trade_expansion:netherite_coin` | 10,000 | R⁴ | 64 |

- 比率は設定 `currency.ratios = [10,10,10,10]`（銅→鉄、鉄→金、金→ダイヤ、ダイヤ→ネザライト）で**段ごとに**指定する。各コインの価値は「その段までの比率の積」（例：金貨 = ratios[0] × ratios[1]）。全段を同じ値にすれば上表の一般式になる。
- ネザライト貨は溶岩で燃えない（ネザライトと同様の `fireResistant`）。
- ツールチップに「価値：1,000c」表示（2枚以上ならスタック合計、下位コインがあれば「スニーク＋右クリックで崩す」の案内も表示）。
  - 注：26.3 では `Item.appendHoverText` が非推奨のため、v0.14（段階11）で Fabric の `ItemTooltipCallback`（クライアント側の `ItemTooltips`）から各アイテムの `addTooltip` を呼ぶ形に置き換えた。
- 各比率は 2〜100 に制限（G章）。最大でもネザライト貨 = 100⁴ = 1億c なので `long` で十分。

#### E-2. 入手方法

| 方法 | 既定 |
|---|---|
| 市場に商品を売る | ON（主な入手手段） |
| 敵モブからのドロップ | ON（`currency.mobDropCoins`）。下記 |
| 鋳造（ブロック→コイン） | ON（`currency.allowMinting`）。**銅貨と鉄貨のみ**。下記 |
| 宝箱 | なし（Q9） |
| エメラルド貨を市場で売る | ON（E-5）。村人交易で得たエメラルドを、相場に応じた少額の銅貨に換える |
| 初回ログイン時の支給 | 0c（`currency.startingMoney`。v0.15 時点で未実装） |

**敵モブのドロップ**（Q22）：

- 対象はエンティティタグ `#trade_expansion:drops_coins`（既定：ゾンビ・スケルトン・クリーパー・クモ等の敵対モブ）。
- **プレイヤーが倒した時だけ**落とす（ルートの条件 `LAST_DAMAGE_PLAYER` があること）。モブトラップでの無限稼ぎを抑えるため。
- 量：銅貨 0〜2枚（ドロップ増加エンチャントのレベル L で、さらに 0〜L 枚。バニラの「レベルごとに最大+1」と同じ考え方、Q22・v0.14.2 で確定）、2.5% で鉄貨1枚。
- 実装（v0.14）：Fabric API の `LootTableEvents.MODIFY_DROPS` で、`entities/` のルートテーブルの結果にコインを足す（ルートテーブル自体は変えない）。`currency.mobDropCoins` が OFF なら足さない。

**鋳造**（3×3 クラフト）：

- 銅ブロック×9 → 銅貨、鉄ブロック×9 → 鉄貨。金貨以上は鋳造できない（交易でのみ手に入る）。
- 出力は**銅換算の価値**で定義する（Q20。今後変更の可能性あり）。独自のレシピ形式 `trade_expansion:minting`（`"value": 640` のように銅換算額を書く）を作り、完成数はその時のコイン比率から `value ÷ コインの価値`（切り捨て、1〜64枚）で計算する。完成数はレシピを読み込んだ時（サーバー起動・`/reload`）のコイン比率で決まるので、比率を変えた後は `/reload` が必要（v0.14）。
  - 既定：鉄ブロック×9 → 640c 分の鉄貨、銅ブロック×9 → 64c 分の銅貨（比率10ならどちらも64枚）。
  - 上限64枚（スタック上限）に当たる場合は価値が減る（例：銅→鉄の比率が5なら 640c ÷ 5 = 128枚 → 64枚＝320c）。
  - 枚数をレシピに固定すると、比率を変えた時に鋳造の価値まで変わってしまう（例：比率100だと鉄貨64枚＝6,400c、鉄インゴット1個あたり約79c となり、市場で 72c で買って鋳造すると儲かる）。銅換算で定義すれば Q8（銅換算固定）と一貫する。
  - 市場で買った素材を鋳造しても損になる条件（鋳造価値 ÷ 81 ＜ そのインゴットの買値）は、`/tradeex audit` で検査している（v0.14。素材のブロックが商品でなくても、インゴット×9 のレシピ経由の買値で計算する）。
- `currency.allowMinting=false` の時はレシピを無効にする（Fabric の Resource Conditions API で設定値を見る独自条件を作る。同じ仕組みをエメラルド貨で実装済み、E-5）。
- コイン比率（E-1）を変えると出力枚数が変わり、銅換算の価値は変わらない（例：比率20なら鉄貨は1枚20cなので、鉄ブロック×9 → 鉄貨32枚）。

※ 3×3クラフトは9枠しかないので **1:10 の両替はクラフトレシピでは作れない**。両替は交易画面の「両替タブ」と、コインを手に持ってスニーク+右クリック（1枚を下位コインに崩す。`currency.sneakUseExchange`）で行う。

#### E-3. 自動両替（支払い・お釣り）

**所持金の対象範囲**：メインインベントリの36枠（ホットバー＋27枠）にあるコイン（v0.9：と財布の残高。財布がある時の支払い・受け取りは E-6）。オフハンド・防具欄・エンダーチェスト等は数えない。付加情報（名前など）付きのコインも価値どおりに数える。

**支払い**（価格 P）：

1. 所持コインの合計価値 `W` を計算。`W < P` なら失敗（`INSUFFICIENT_FUNDS`）。
2. **所持コインをいったん全部回収**する。
3. 残額 `W − P` を、**大きいコインから貪欲法**で返す（各コインの価値は下位コインの整数倍なので、貪欲法で最小枚数になる）。
4. 返却はインベントリへ。入りきらなければ足元にドロップ（`ItemEntity`。当面は誰でも拾える、Q16）。

- この方式は所持コインの組み合わせに関係なく常に正しく支払える（例：ダイヤ貨2枚で 1,080c → 回収 2,000c、返却 920c＝金貨9・鉄貨2）。
- 返却枚数は各コイン種「比率−1」枚以下（最上位を除く）なので、最大でも5種類＝通常5枠程度で収まる（比率が64を超える設定では1種類が2枠になることがある）。
- 実装上は、所持金などの検証をすべて済ませてから回収・付与を行う（検証後に失敗する処理が無いので、元に戻す処理は持たない）。返却はゲーム標準の `placeItemBackInInventory` で行い、入りきらない分は自動で足元にドロップされる。手順はすべてサーバーの1回の処理内で行う。
- **購入時の順序（v0.4 確定）**：①所持金・空き枠を検証（失敗ならここで中止し、何も変えない）→ ②コインを全部回収 → ③**商品を先に渡す** → ④お釣りを返す。商品の空き枠判定では、回収されるコインの枠を空きとして数える。商品は検証済みなので必ず入り、入りきらない可能性があるのはお釣りだけになる（溢れたお釣りは足元にドロップ）。
- **副作用（仕様とする）**：支払いのたびに手持ちコインが最小枚数に整理される（例：銅貨200枚を持って 1c 払うと、金貨1・鉄貨9・銅貨9 になる）。
- ドロップしたお釣りは当面は誰でも拾える（Q16）。取引したプレイヤーだけが数秒間拾える制限は今後のバージョンで検討する。

**受け取り**（売却額 Q）：大きいコインから貪欲法で支払う（最小枚数。Q15 で決定、小さいコイン優先の設定は設けない）。売却時はアイテムを先に取り除いてからコインを渡す。

**端数**：価格は常に銅貨単位の整数なので端数は発生しない（丸めは B-2 で実施）。

**両替タブ**：上位↔下位の1段変換。手数料 `currency.exchangeFee`（既定 0%）。まとめる時は払う下位コインを ceil(枚数 × 比率 × (1 + 手数料))、崩す時は受け取る下位コインを floor(枚数 × 比率 × (1 − 手数料)) にする（v0.14、`ExchangeService`）。財布の中のコインは使わず、インベントリのコインだけを対象にする（受け取ったコインもインベントリへ。入りきらなければ足元に落とす）。1回の枚数は最大640枚。交易画面を開いていて、交易所の近くにいる時だけ（クリエイティブ不可は取引と同じ）。

#### E-4. 比率変更時の影響（Q8）

**銅換算固定**（Q8 で決定）：商品価格は銅貨単位で定義・保存されるため、比率を10→20に変えると
- 商品の銅換算価格は変わらない（パン20c のまま）。
- 上位コインの価値が変わる（金貨 100c → 400c）。**既に持っている金貨の価値が4倍になる**。

そのため：
- 比率はワールド作成時に決める前提とし、変更時はサーバーログに警告。
- 不採用とした別案「コイン表記固定」は、価格を「金貨1枚」のように上位コインで定義し、比率変更で銅換算が変わる方式。ゲーム途中の比率変更に強いが、価格表示がブレる。
- 設定 `currency.ratioLocked=true` で、ワールド作成後の比率変更を拒否（保存データ側の比率を優先）するオプションを用意。

#### E-5. エメラルド貨（補助コイン）【v0.6 追加】

村人交易でいくらでも手に入るエメラルドを、このModの経済に**少しずつ**取り込むための補助コイン（Q23〜Q26）。

| 項目 | 内容 |
|---|---|
| ID | `trade_expansion:emerald_coin`（スタック 64） |
| 入手 | エメラルドブロック1個 → エメラルド貨1枚（**石切台**、一方通行。Q24）。不定形クラフトだとバニラの「エメラルドブロック→エメラルド9個」と材料が同じで衝突するため、石切台のレシピにする（v0.8）。枚数は `currency.emeraldCoinsPerBlock`（既定1、範囲 0〜64）。レシピ形式 `trade_expansion:emerald_coin`（石切台レシピの派生）が、レシピを読み込む時（サーバー起動・`/reload`）に設定値を完成数にする。0 の時は Fabric の読み込み条件 `trade_expansion:emerald_coin_enabled` でレシピ自体を読み込まない（v0.11、段階8） |
| 所持金 | **数えない**。支払い・お釣り・両替タブ・スニーク崩しの対象外（`WalletService` が数えるのは E-1 の5種のみ） |
| 使い道 | 市場で売却して銅貨に換えるだけ（案B、Q25）。購入は不可（`buy: false`） |
| 扱う市場 | **村の市場だけ**（Q26）。市場を作った時に、中心が村の構造物（`#minecraft:village`）の中にあれば扱う（`auto_add` 条件、商品数 `N` とは別枠）。ネザー・エンドやプレイヤーが村の外に作った町の市場では扱わない |

**商品定義（既定）**：

```json
// data/trade_expansion/trade_expansion/goods/emerald_coin.json
{
  "item": "trade_expansion:emerald_coin",
  "unit": 10,
  "base_price": 5,
  "elasticity": 128,
  "target_stock": 0,
  "max_stock": 64,
  "restock_per_day": 64,
  "buy": false,
  "sell": true,
  "auto_add": [
    { "type": "trade_expansion:structure", "structure": "#minecraft:village" }
  ]
}
```

- 平常時の売値は 10枚で 4c（1枚 0.4c。既定ではエメラルド貨1枚＝エメラルド9個なので、エメラルド1個あたり約 0.04c）。売るほど X が上がって値下がりする（B-2）。
- 在庫は目標 0 に向かって1日 32単位ずつ減る（B-3 の消費量 c。消耗品ではないので既定の `r/2`＝64÷2）。上限 64単位（640枚）に達すると買取停止。つまり**1市場で換金できるのは1日あたり約320枚（32単位 × 最大4c ＝ 最大128c、実際は値下がりでそれ以下）まで**に自然と抑えられる。
- 購入できないので、同一市場での売り買い往復（B-6）は起こらない。
- 地域間の価格差で儲ける遊び（Q7）の対象にはならない（どこでも買えないため）。
- 村人交易を無効化する設定（Q5）を使うとエメラルドの入手が減るが、エメラルド貨の仕組みはそのまま使える。
- 村の判定は「市場の中心が村の構造物の範囲内か」なので、村の外れに作った市場は村の市場にならないことがある。村の中に置いた屋台は既存の村の市場に所属する（C-1）ので、通常は問題にならない。
- `currency.emeraldCoinsPerBlock` を増やすとエメラルド貨が作りやすくなるが、換金できる量は市場の在庫上限で抑えられる（上記）ため、経済への影響は小さい。

#### E-6. 財布【v0.9 追加】

インベントリにコインが増えて場所を取らないよう、コインを**金額として**しまっておくアイテム（Q28）。

| 項目 | 内容 |
|---|---|
| ID | `trade_expansion:wallet`（スタック 1） |
| 入手 | クラフト（革×5＋糸×2。Q32） |
| 中身 | **金額（c）だけを記録**する（データコンポーネント `trade_expansion:wallet_balance`、long）。コインの枚数ではなく銅換算の金額なので、コイン比率を変えても中身の価値は変わらない（Q8） |
| 容量 | `wallet.capacity`（既定 100,000c ＝ネザライト貨10枚分）。超える分はコインのまま残る |
| 入れ方 | ①コインを財布の上に重ねる（カーソルで持ったコインを財布の上で右クリック、またはその逆。バンドルと同じ操作）②**自動収納**：財布をメインインベントリに持っている間、**拾ったコイン**を自動で財布に入れる（`wallet.autoCollect`、既定 ON）。拾う処理に Mixin（`ItemEntity.playerTouch`）で割り込む。財布から取り出したコインがすぐ財布に戻らないよう、すでにインベントリにあるコインは自動では入れない ③取引のお釣り・売却代金は財布に入る |

| ツールチップ | 「残高：12,345c ／ 容量 100,000c」と、入れ方・出し方の案内 |
| 死亡時 | 普通のアイテムと同じくドロップする（**中のお金ごと失うリスクがある**。安全に持ちたいなら銀行へ） |
| 複数持っている時 | 所持金には全部の財布を数える。支払いはメインインベントリの順に財布から引き、受け取りも同じ順に各財布の容量まで入れる |

**所持金と支払いの変更**（E-3 を拡張）：

- 所持金 ＝ メインインベントリのコイン ＋ メインインベントリにある全財布の残高。
- **支払い**：①財布から支払う（複数あればインベントリの順に）→ ②財布で足りなければ、残りを E-3 の方式でコインから払い（コインを全部回収）、お釣りは財布に入れる（入らない分はコイン）。v0.11：「手持ちのコインを先に財布に入れる」手順は省いた（結果は同じで、コインを財布に入れたい時は重ねる操作で入れる）。
- **受け取り**（売却代金・お釣り）：財布があれば財布に入れる。容量を超えた分だけコインで渡す。財布が無ければ従来どおりコイン。
- 結果として、財布を持っていればコインはほとんどインベントリに出てこない。

銀行に預けたお金を、**どの市場でも**直接使うためのカード（Q29。実際の動きはデビットカード）。

| 項目 | 内容 |
|---|---|
| ID | `trade_expansion:bank_card`（スタック 1） |

### F. データ保存・マルチ対応

#### F-1. 永続化

- `SavedData` を **サーバー全体の SavedDataStorage**（`MinecraftServer.getDataStorage()`）に1つ。ID は `trade_expansion:markets`。全次元の市場を保持（各市場が次元IDを持つ）。（確認済：付録A）
  - 定義：`new SavedDataType<>(Identifier, MarketRegistry::new, CODEC, null)`。第4引数（データ変換の種類 `DataFixTypes`）は null。バニラの読み込み処理は null だと例外になるが、Fabric API（`fabric-object-builder-api-v1` の `SavedDataStorageMixin`）が null の時は変換を飛ばすため問題ない。将来データ形式を変える時は `schemaVersion` を見て自前で移行する。
  - 保存形式は Codec（NBT）。フィールド名は snake_case（`schema_version`, `currency_ratios`, `next_id`, `markets`、市場は `id`, `dimension`, `center`, `origin`, `profile`, `level`, `last_level_check`, `stalls`, `last_update`, `goods`、v0.15 で `naming{name, namer}`（C-4）、v0.14 で `requests`, `last_request_refresh`, `next_request_id`, `shortages`（`goods`・`multiplier` のリスト）, `shortage_period`、商品は `item` と `state{price_factor, pressure, stock, last_trade, history, last_sample_day}`）。v0.14・v0.15 で増えた項目はどれも省略可（無ければ既定値）なので、`schema_version` は 2 のまま。`schema_version` 2（段階7）から商品は**商品ID**（`trade_expansion:bread`）で記録する。フィールド名は互換のため `item` のまま。版1のデータ（アイテムIDで記録）は読み込み時に `minecraft:bread` → `trade_expansion:bread` のように自動で移行する。商品は表示順を保つため Map ではなくリストで保存する。
- 構造：

```
MarketRegistry
 ├ schemaVersion: int
 ├ currencyRatios: int[4]           … E-4 用
 ├ nextId: long
 └ markets: Map<MarketId, Market>
     Market
      ├ id, dimension, center(BlockPos), profileId, origin
      ├ stallPositions: Set<BlockPos>
      ├ level: int, lastLevelCheckGameTime: long   … D-4
      ├ requests: List<Request>, lastRequestRefresh: long, nextRequestId: int   … J章（v0.12、段階13）
      ├ shortages: Map<GoodsId, multiplier>, shortagePeriod: long   … K章（v0.12、段階13）
      ├ name: String?（無ければ自動の名前）, namer: UUID?   … C-4（v0.15）
      ├ lastUpdateGameTime: long
      └ goods: Map<GoodsId, GoodState>
           GoodState { priceFactor(double), X(double), S(double), lastTradeGameTime, history: List<X>（最大14日）, lastSampleDay }   … 基準価格 B は保存せず D-1 の式で計算。history は相場グラフ用（A-4。1日1回、市場の更新時に X を記録）
```
- 書き込み：取引時に `setDirty()`。保存はバニラの自動保存に任せる。
- 【v0.9】銀行口座は別の SavedData `trade_expansion:bank`（サーバー全体に1つ）：`accounts: Map<UUID, Account>`、`Account { balance: long, cardNumber: int }`。財布の残高はアイテム側（データコンポーネント）に持つので、保存データには入らない。
- 交易所ブロックエンティティは `market_id`（未割当は `-1`。自然生成品は最初の右クリックまで未割当、A-3）と `origin`（`natural`/`crafted`。v0.4.1 で追加、段階8で実装済み。割り当て直しの判定に使う。保存されていない古い屋台は A-3 のとおり補う）を保存。【v0.16、段階10】紐付いた商人NPCの UUID（`trader`）も保存する。商人NPC 側は `market_id`・紐付いた交易所の座標 `stall`（①④のみ）・`link_nearby_stall`（村の建物で置かれ、まだ紐付けていない印）を自分のエンティティデータに持つ（保存データには入らない）。
- データパックで定義が消えた商品は状態を残したまま「非表示」にする（再追加で復活）。

- 画面は `AbstractContainerMenu` ＋ `ExtendedMenuType`（`fabric-menu-api-v1`。開く時に `OpenData(市場ID, 屋台の座標, 商人のエンティティID)` を渡す。交易所から開いた時は商人のIDが -1。【v0.16、段階10】商人NPCから開く場合は画面の有効性を商人で判定する（商人が生きていて `trade.maxDistance` 以内、A-5）。メニューはプレイヤーインベントリと売却スロット1枠を持つ（v0.14、A-4）。（確認済：付録A）
- サーバー側で必ず検証：プレイヤーが開いている画面の市場IDが要求と一致、屋台が存在し `trade.maxDistance`（既定8）以内、数量が 1〜`trade.maxPerTransaction`（Shift で全数の時は 2,304）、アイテム実在（B-5 の結果コード参照）。
- 同時取引：サーバーのメインスレッドで処理するので排他は不要。Fabric の `ServerPlayNetworking` の受信処理は最初からサーバースレッドで呼ばれるため、`server.execute()` は不要（Fabric の仕様からの判断で、実機では未確認）。

### H. 村人交易のコイン化【v0.12 追加、段階14】

村人の交易を、このModの経済につなげる（Q36）。v0.12 で Q5「村人交易は触らない」の方針を変更した。

#### H-1. 方針

| 方向 | 内容 |
|---|---|
| 村人から**買う**（プレイヤーが払う） | 代金をエメラルドから**コイン**に変える |
| 村人に**売る**（プレイヤーが受け取る） | 今までどおり**エメラルド**で受け取る |
| エメラルドの行き先 | エメラルド → エメラルドブロック（バニラ）→ エメラルド貨（石切台、E-5）→ 村の市場で売って銅貨に換える（相場で変動、Q23） |

- 村人に売って得たエメラルドは、エメラルド貨を通して少しずつしか銅貨にならない（E-5 の換金量の上限）。一方、村人から買うにはコインが必要なので、村人交易がコインの使い道（お金が減る先）になる。
- バニラの取引の仕組み（1つの取引＝決まった品と数）は残し、代金の品と数だけをコインに置き換える。

#### H-2. 換算（既定案、今後調整）

- 代金 ＝ `ceil(エメラルドの数 × villager.emeraldPrice)`（c）。`villager.emeraldPrice` の既定は 30c（仮）。
- 職業レベル・バニラの評判による値引き・需要による値上げは、**バニラが計算したエメラルドの数**に対して換算する（値引きの仕組みはバニラのまま）。
- **抜け道の注意**：換算が安すぎると「村人から安く買って市場で高く売る」抜け道になる（例：1エメラルド＝5c だと、パン6個を 5c で買い、市場で1個 16c で売れる）。対策の候補：
  - 案A：その品が市場の商品なら、代金を「最寄りの市場の買値 × 数量」以上にする（下限）
  - 案B：市場の商品と同じ品は、村人の売り物から外す
  - 既定は案A。値は今後のバランス調整で決める（Q36）。

#### H-3. 支払い

- 取引画面の代金の欄にコインを表示し、取引を確定すると E-6 と同じ順（財布 → コイン）で自動的に払う。カードは使わない（村人は銀行と無関係）。
- 実装には Mixin（取引の代金の表示・判定・支払い）が必要。

#### H-4. 段階の分け方（Q36）

| 段階 | 内容 |
|---|---|
| 14a | 代金のコイン換算と表示、財布・コインからの自動支払い（職業・評判の値引きはバニラの値をそのまま換算） |
| 14b | 行商人・特殊な取引（宝の地図など）の扱い、`villager.coinTrades` の ON/OFF |
| 14c | 抜け道対策（H-2 案A）と換算のバランス調整 |

- 設定 `villager.coinTrades`（既定 true）でコイン化を切り替える。`vanilla.disableVillagerTrades`（村人交易そのものを無効化）は残す。

### I. 掲示板【v0.12 追加、段階13】

交易画面の「掲示板」タブで、**近くのほかの市場の最新の価格**を見られる（Q37）。

| 項目 | 内容 |
|---|---|
| 対象の市場 | 同じ次元で、今の市場の中心から水平 `board.radius`（既定 512、設定で変更可）以内の市場。近い順に最大 `board.maxMarkets`（既定 20）件。今の市場は除く |
| 価格 | **最新**（サーバーがその場で遅延回復を計算した値、B-3） |
| 商品 | その市場の**すべての商品**（買値・売値・在庫の状態・不足品の印 K） |
| 表示 | 市場ごとに「麦の里（町）・北東 340m」のように市場名（C-4）・レベル名・方角と距離を出し、選ぶと商品の一覧を表示 |
| 通信 | タブを開いた時に `BoardRequestC2S`（市場ID）→ `BoardS2C`（市場ごとの商品と価格）。開いている間は更新しない（再度開くと最新） |
| 費用 | 無料 |

- 価格だけを見る機能で、離れた市場とは取引できない。
- 地域間の価格差で儲ける遊び（Q7）が分かりやすくなる。512ブロックより遠い市場は、実際に行かないと分からない。

### J. 依頼【v0.12 追加、段階13】

市場がランダムに「この品を何個納めてほしい」という依頼を出し、納めると報酬のコインがもらえる（Q40）。数値はすべて既定案で、今後調整する。

| 項目 | 内容（既定案） |
|---|---|
| 依頼の数 | 1市場に最大 `quest.maxPerMarket`（既定 3）件 |
| 入れ替え | ゲーム内 `quest.refreshDays`（既定 1日）ごとに、期限切れ・達成済みの枠を新しい依頼で埋める（画面を開いた時にまとめて計算する、遅延評価） |
| 依頼の品 | 商品定義（D-2）の品から抽選。**その市場がプレイヤーに売っていない品**（扱っていない、または `buy: false`）を優先する（同じ市場で買って納めるだけで儲かるのを防ぐ）。対象は取引単位1で `auto_add` が無く（補助コインのエメラルド貨などを除く）、付加情報（`components`）の無い商品だけ。同じ品の依頼は同時に2件出さない（v0.14） |
| 数量 | 1〜その品の目標在庫 T（最低 1）から抽選 |
| 難易度 | ★1〜3。依頼の金額 `B × 数量` で決める：200c 未満＝★1、1,000c 未満＝★2、それ以上＝★3（`quest.difficultyThresholds`）。品のグレード（goods-design 1-3）は商品定義の項目に無いため、金額で判定する（v0.12.1） |
| 報酬 | `ceil(基準価格 B × 数量 × 難易度の倍率)`。倍率は ★1＝1.2、★2＝1.5、★3＝2.0（`quest.rewardMultipliers`）。B は依頼を出した市場のもの。その市場が扱っていない品の B は「商品定義の base_price × その市場のプロファイルの倍率（D-1）× price.globalMultiplier」とし、ばらつき（priceFactor）は 1 として計算する（priceFactor は扱っている商品にしか無いため、v0.12.1） |
| 期限 | ゲーム内 `quest.durationDays`（既定 3日） |
| 受け方 | 交易画面の「依頼」タブに一覧を出す。**誰でも納品できる（先着）**。受注の手続きは無い |
| 納品 | 「納品する」で、必要な数の通常品（付加情報なし）をインベントリから取り除き、報酬を財布 → コインで受け取る（カード払いを選んでいれば口座へ、E-8）。足りなければ納品できない |
| 納めた品 | 消費される（市場の在庫には入らない） |

- 報酬は新しく生まれるお金なので、依頼の数・入れ替え頻度・倍率でお金の増え方を抑える。抜け道（依頼の品を別の市場で安く買って納める等）は、地域間の価格差を使う遊び（Q7）でもあるので禁止はせず、倍率で調整する（Q40）。
- 評判（L-2）を作る時は、依頼の達成で評判が上がる形にする想定。

### K. 需要（不足品）【v0.12 追加、段階13】

市場ごとに「不足している品」があり、その品は高く買い取ってもらえる（Q42）。数値はすべて既定案で、今後調整する。

| 項目 | 内容（既定案） |
|---|---|
| 不足品の数 | 1市場に最大 `demand.maxShortages`（既定 2）品 |
| 選び方 | その市場が扱っていて、プレイヤーが売れる（`sell: true`）商品から抽選。取引単位1で `auto_add` の無い商品だけ（補助コインのエメラルド貨などを除く、v0.14） |
| 期間 | ゲーム内 `demand.durationDays`（既定 3日）ごとに選び直す。乱数のシードは `市場のシード ^ (期間の番号 × 定数)`（期間の番号は `floor(時刻 ÷ 期間)`） |
| 効果 | その市場でのその品の基準価格 B に `demand.multiplier`（既定 1.5〜2.0 の間で抽選）を掛ける。買値・売値の両方が上がる（品が足りないので売っても高い） |
| 伝わり方 | B への倍率なので、ほかの市場には伝わらない（相場 X の波及 C-2 とは別） |
| 表示 | 交易画面の一覧と掲示板（I）に「不足」の印 |
| リセット・選び直し | `market reset` は不足品と依頼をそのまま残す。`market reroll` は商品構成が変わるので、不足品と依頼も選び直す（v0.12.1） |

- 不足品はプロファイルの価格倍率と同じく B に掛かるので、プレビュー（F-2）にもそのまま反映される。
- **クラフトの原則の例外**：商品設計書 1-1「同じ市場で素材を買ってクラフトしても儲からない」は、不足品では成り立たないことがある（例：パン不足 ×2 なら、小麦を買ってパンにして売ると儲かる）。これは「不足品はクラフトで稼ぐ機会」として認める。在庫の上限（Scap）があるので、1つの市場で稼げる量は限られる（Q42）。

### L. 保留中の仕様【v0.12 記録】

方針だけ記録し、決まったら本文に移す。

#### L-1. 村のレベルの条件（Q38、保留）

案：
- オーバーワールド：市場から半径64ブロック以内に、**村人と紐付いているベッド**（村人が使っているベッド＝ `minecraft:home` POI の占有あり）が1つ以上あることを必須にする。
- ネザー・エンド：ベッドの代わりに**職業ブロック**を使う。村人と紐付いている職業ブロックが1つ以上あることを必須にする。

検討点：
- 条件を満たさない市場の扱い（レベル1のまま／ベッドを数えない／市場として扱わない）。
- プレイヤーの拠点（村人がいない）は条件を満たせないので、D-4「プレイヤーが作った町も家を建てるほど育つ」、銀行が使えるレベル3（E-7）と食い違う。
- ネザー・エンドの測り方（Q27 の「村人の人数」）を、職業ブロックの数に置き換えるのか、人数のまま「職業ブロックが1つ以上」を条件に足すのか。

#### L-2. 評判（Q39、保留）

案：村（市場）ごとに信用値を持つ。

検討点：
- 何で上下するか（取引の量・依頼の達成・期間）、村ごとか「村 × プレイヤー」ごとか。
- 何に効くか。**価格の割引に使う場合**はプレイヤーごとに価格が変わるため、スナップショット（F-2）を人ごとに送る作りに変える必要がある。また割引で買値と売値の差が縮むと、B-6（同じ市場での往復で儲からない条件）が崩れることがあるので、割引に上限が必要。
- 価格以外の効果（依頼の解放、銀行・カードの手数料など）なら、今の仕組みとぶつからない。
- バニラの村人の評判（ゴシップ）とは別のものとする。

## 4. クラス構成・パッケージ構成

### 4-1. 方針
- **価格計算・距離計算・通貨計算は Minecraft に依存しない純Javaクラス**にする → JUnitで高速テスト可能。
- Minecraft依存部分（登録・画面・通信・保存）は薄く。

### 4-2. パッケージ

テンプレートの `splitEnvironmentSourceSets()` に従い、**共通（サーバーでも動く）コードは `src/main/java`、クライアント専用コード（画面・描画・クライアント受信）は `src/client/java`** に置く。共通側からクライアント専用クラスを参照すると、専用サーバーで起動した時にクラッシュするので禁止（ビルド時にも検出される）。

### 4-3. データフロー（売却の例）

```
[Client] MarketScreen：数量10選択 → ClientMarketCacheの値でプレビュー表示（5,517c）
   │ [売却する] TradeRequestC2S(market=12, goods=trade_expansion:diamond_sword, SELL, qty=10, expected=5517, card=false)
   ▼
[Server] ModPayloads の受信処理（サーバースレッド）→ TradeService.handle()
    1. 検証：メニュー一致・数量≤上限 → 距離（stillValid）→ クリエイティブ可否 → カードの有効性 → 取扱可（B-5 の順序）
    2. Market.refresh(now)        … B-3 遅延回復
    3. S+10≤Scap を確認 → PriceModel.sumSell(params, X, 10) → 5517
    4. 期待額と比較（ずれ > tolerance → 失敗 PRICE_CHANGED）
    5. 所持数≥10 を確認 → InventoryUtil.remove(商品の一致条件, 剣10本。売却スロットも対象) → 代金 5517c を渡す（財布 → コイン、溢れはドロップ。カード払いなら口座へ）
    6. PriceModel.applySell：X += 10, S += 10
    7. Propagation.apply(registry, market, goods, ΔX=10) … 同次元の全市場を走査し、各市場 refresh 後に X += ΔX×w(d)
    8. MarketRegistry.setDirty(), ログ出力
    9. TradeResultS2C(成功) ＋ AccountS2C → 本人
       MarketSnapshotS2C → この市場/波及先の画面を開いている全プレイヤー（差分ではなく全体、Q19）
       ※ 失敗時は TradeResultS2C(失敗コード) ＋ 最新 MarketSnapshotS2C を本人へ
   ▼
[Client] ClientMarketCache更新 → 画面再描画（価格・最大数量はクライアントの PriceModel で再計算）
```

## 付録：用語
- **c**：銅貨単位（copper）。全ての価格の内部単位。
- **市場（Market）**：交易所の集まり。在庫と相場を共有する単位。
- **商人NPC**：交易所と同じ交易画面を開く独自のNPC。村人とは別物（A-5）。
- **相場（X / V）**：需給圧と、それによる価値倍率。
- **波及**：ある市場の取引が、近くの市場の相場に距離に応じて影響すること。
- **財布**：コインを金額としてしまっておくアイテム（E-6）。
- **銀行・カード**：プレイヤーごとの口座と、その残高でどの市場でも払えるカード（E-7・E-8）。
- **補助コイン**：所持金に数えず、市場で売って銅貨に換えるコイン。エメラルド貨のみ（E-5）。
- **市場レベル**：市場の周りのベッド数（ネザー・エンドは村人の人数）で決まる規模（1 集落〜5 都市）。扱う商品の数と種類が変わる（D-4）。
- **消耗品**：食料・松明・燃料・原木など、市場で使われてなくなる品。在庫と相場が早く戻る（B-3）。
- **市場名・名付け親**：市場に付けた名前と、それを変えられるプレイヤー（C-4）。
